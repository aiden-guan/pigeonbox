# Ambient compose context

## Audit and implementation boundary

The extension and the server share the `shared`, `api-contract`, `cloud-client`, AI and tracker workspace packages in this repository; the server imports them directly, so a contract change reaches both sides in one commit.

The old local classifier required a day/time/numeric/name anchor. Live retrieval restricted strong evidence to recipients, the current thread or corrected facts, used a compressed owner profile for other consumers, and only enabled embeddings for anchored factual claims. Calendar cache contained metadata for 36 hours, no FTS/vector, and could retain removed events. Model output was checked for source IDs, but its advisory assertion itself was not grounded.

The implementation extends the same compose route, worker bridge, preference, canonical `getRelevantContext`, encrypted facts/summaries/notes, relationship events, commitments, search vectors, optional Fast Recall, metered inference and rate-limit store. It does not introduce a Brain database or replace draft/search pipelines.

## Pipeline

1. The shared synchronous `detectComposeContext` first excludes questions, opinions/preferences, hypotheticals, links and quoted text. It prefers the existing specific classifier, then recognizes objective status, negative existence, uncertainty, prior references, temporal context and interaction history. A broad personal/objective-assertion fallback admits unfamiliar wording without recognizing specific sentences. A hint is routing data only. It is never a truth judgment.
2. Gmail input handling restarts the existing 900 ms idle timer and invalidates the request generation. After idle, the controller reads user prose, skips quoted/forwarded/signature/UI/reopened-draft content and selects a fresh clause near the caret. Only a bounded clause (700 characters) plus subject, recipients, mailbox/thread and hint is transported through the extension's background worker, signed in to your server. The 2.8 s cooldown, per-key in-flight deduplication and 30-second per-compose memory cache (continuations are never cached) remain; destruction clears them.
3. The server enforces 30 checks/minute, loads the authenticated user's preference/account/thread under RLS, independently derives the candidate and checks `safeMemoryText`. Calendar availability/scheduling still use real free/busy without inference. Explicit current-thread deadlines precede retrieval.
4. Exact retrieval runs before embeddings: active sourceable individual self/person/topic facts, current summaries, open promises, user notes, relevant interactions and fresh future calendar metadata. Calendar FTS and event names linked by reliable retrieved facts rank ahead of unrelated earlier events. Contacts resolve actual unique names and supply user-authored notes, never factual proof by themselves. The current-thread exception does not bypass live forget exclusions. Sources are batched; live memory decryption is capped at 12 candidates, then selection at 8 items/1,400 conservative context tokens. Ranking/provenance remains internal.
5. General assertions and dated calendar context also retrieve up to 50 current primary-calendar events from an authorized connected account, reduced to four ephemeral metadata items. Date/daypart/clock parsing bounds retrieval; the judgment interprets meaning, event category and exceptions. Cancelled, declined, tentative, unaccepted and ended events cannot establish attendance. Live events are read again after judgment before showing a notice. This path does not persist events or prose, infer availability from missing events, or force a notice from a sentence pattern. Corrected/replacing fact values, earlier commitments, exact named event existence, exact high-confidence owner status and explicit recent interaction conflicts can decide without a model. Availability alternatives still come only from `proposeSlots`.
6. General assertions use semantic retrieval even when live calendar evidence exists. If no strong exact proof remains, other accepted general/factual candidates can use the existing query embedding and indexes without requiring a numeric/date anchor. The live query uses only the clause, has a two-second embedding timeout and is never persisted. Embedding entitlement/rate/budget failures fall back to exact context. The original provider and 768-dimensional vectors remain.
7. Evidence needs a specific topic/entity/thread/recipient/self tie, confidence >=0.90, current status, safe text and temporal validity. Strong semantic similarity plus an authorized self/thread/recipient/entity scope can admit an unfamiliar factual assertion to judgment. Live calendar metadata does not need lexical overlap; chronological validation still applies and the model must establish relevance. Owner scope alone is insufficient. An opaque calendar name can be linked to a retrieved source explaining its topic; `CalHacks` alone never proves “hackathon.” Negative future existence needs an actual current event or an explicit dated owner participation fact; a category fact alone does not prove attendance. Ambiguous contact names fail closed.
8. One `compose_check` judgment uses the configured primary model (`CLOUD_AI_PRIMARY_MODEL`), Standard tier, reasoning none and at most 200 output tokens for checks, or 440 when a continuation is requested. Evidence wire data, including approved advisory sentences, is capped separately at 1,400 conservative tokens, at most 8 items, 400 text characters/item, 120 title characters and 4 cited sources. No structured-output repair, provider optional-parameter retry or model fallback is allowed for this operation. The seven-second total semantic deadline bounds the remaining model time.
9. Thresholds are 0.90 for contradictions, 0.93 for overlooked/legacy context and 0.96 for helpful context. A semantic message must copy a complete selected source sentence or a server-rendered structured calendar sentence verbatim. Splicing, paraphrasing, polarity changes, invented numbers/names/dates and unknown citations fail validation. This makes the model a relevance judge, not a factual author. One-click suggestions may replace only one supported objective value; the existing numeric/date grounding guard remains. Sources, versions, revisions, ownership, availability of the connection, opt-in, Fast Recall state and forget/deletion exclusions are checked again after arbitration.
Clients that omit ambient routing hints receive `context` for `overlooked_context`/`helpful_context` notices, preserving their original response schema and the same proof, severity and text. Hint values remain untrusted routing data; the server re-derives the assertion.
10. The UI underlines the correction diff first, then an exact unique `highlightText` (<=160 characters, no HTML/links), then the clause. Literal ranges can span inline formatting without editing Gmail DOM. The existing subtle dot/popover, keyboard actions, restricted Gmail/Calendar source links, undo and suggestion behavior remain. No panel, send hook or autonomous sending is added.

## Cost and privacy

Social prose, questions and subjective preferences are excluded. Objective or personal assertions can create idle compose requests, including unfamiliar wording. Accepted requests do no work per keystroke and prefer deterministic/exact checks. Semantic retrieval has separate attempt limits of 12/minute and 600/UTC day. Arbitration has limits of 12/minute and 600/UTC day. Existing per-user daily/monthly AI and global budgets/rates also apply; deterministic checks remain available when inference is capped. Caps count attempts, including unsuccessful inference attempts.

The clause, query vector, evidence pack, advisory and suggestion live only in request/compose memory. No live prose is stored as memory, browser storage, durable job data, logs, usage rows or a server response cache. Operational rate counters and content-free usage records are retained normally. Background indexing stores vectors derived only from existing calendar title/location/time metadata; no descriptions or raw mail are copied. Sensitive/credential/financial-identifier/injection restrictions remain unchanged. Fast Recall retains its separate opt-in/encryption/retention/delete behavior.

Logging records IDs, candidate category, decision path, selected count, semantic/model flags, notice count, latency and safe errors only. Provider error details are omitted for compose arbitration. Local mode requires none of these server services.

## Additive database change

`20261008054105_ambient_calendar_context.sql` extends `calendar_event_cache` with generated FTS over existing title/location metadata, an indexed 768-dimensional vector, model and content hash. `search_documents` is thread-owned with a mandatory thread FK, so it cannot represent an event cleanly. Reusing the calendar cache avoids a second table/plaintext copy. Existing owned account/profile FKs, cascade deletion and `app.protect_user_table` RLS remain in force. An invoker trigger invalidates vectors on metadata changes, cancellation or decline; its execution is denied to public/anon/authenticated roles.

The existing 15-minute `calendar.refresh` job fetches a bounded 45-day/250-event window and indexes at most 32 missing/current-model events per batch, using existing metering, encryption boundaries and vectors. Unchanged events are not embedded again. Complete listings remove missing cached events; a truncated listing never proves deletion or absence, and unrefreshed entries age out of live eligibility after 30 minutes. Cancelled events are removed, declined/tentative entries cannot assert attendance, and stale metadata cannot support a notice. No live request backfills events or fetches arbitrary Gmail history.

Verify this migration is applied before deploying this server revision. Normal calendar refresh populates search data gradually; no new secret, environment flag, provider, cron, user preference or backfill command is needed.

## Verification scope and remaining limitations

Offline evals use synthetic Gmail and controlled extraction/judgment with actual routing, SQL/PGlite migrations, RLS, encryption, provenance, vectors and metering. Public tests cover the positive/negative candidate set, payload bounds, highlight validation, multi-node ranges, caches, stale generations, Local mode and existing compose behavior. Chromium fixtures cover the exact CalHacks highlight/source interaction alongside existing undo, Tab/Escape, tracking and placeholder checks.

These fixtures establish mechanics, not live-model semantic precision or installed real-Gmail behavior. Live-provider evals have not been run or credentials recovered. Bounded retrieval can miss facts, and extractive-message validation yields source wording rather than an ideal paraphrase. Calendar descriptions are intentionally absent; classification such as “CalHacks is a hackathon” must come from title metadata or another reliable source. Cache freshness depends on the existing refresh job, the current primary-calendar integration and bounded listing/indexing windows. An already-returned notice can remain in the 30-second per-compose advisory cache after a later remote source change; there is no cross-window invalidation channel. There is no just-in-time old-email expansion. Owner facts/notes outside the bounded shortlist may require semantic retrieval or remain unseen. Existing broad thread-level forget exclusions can hide otherwise useful context. Sensitive filtering is the existing deterministic policy, not a complete semantic DLP classifier.
