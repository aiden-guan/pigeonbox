# Memory conversations and promise reconciliation

The dashboard Memory page keeps its overview visible and starts fact groups closed. The former Projects label is Work & plans. Expanded groups stay open during a save. Ask or update supports questions and explicit Remember, Update and Forget requests. The first save and last forget keep their confirmation visible.

`POST /v1/memory/chat` requires the signed-in owner and the `cloud_ai` capability. Questions retrieve bounded active memory; a selected page contributes context alongside relevant facts elsewhere. Conversation history and saved data are untrusted evidence. Only the latest explicit owner request can authorize a change. Server checks validate handles, exact authorization spans, existing ownership/revisions, allowed text and person identity before an atomic write. Confirmations describe committed changes. User-saved facts use the existing encrypted store, corrected-fact semantics, reindexing and consolidation; they remain usable when automatic learning is off. Questions, chat history and query vectors are ephemeral. They do not authorize mail actions.

`intel/commitment-reconciliation.ts` runs after eligible nonbulk thread analysis and on retries when classification already finished. It compares open promises for that account/correspondent against later synced message text, recipients, direction and attachment filenames, including delivery in another Gmail thread. Promise references point to the original statement where identifiable, rather than whichever email happened to be last when analyzed.

Structured inference identifies semantic fulfillment or explicit withdrawal. Persistence requires a known promise/message handle, confidence at least 0.9, exact evidence, later chronology, the responsible author and correct correspondent, and a current account/thread version. A document promise also requires an observable attachment or delivery link. An unrelated PDF, acknowledgement, another promise or partial progress should remain open. Gmail attachment contents are not fetched or inferred from filenames. Budget or final provider failures leave promises open; transient failures can retry the analysis job.

Completion updates the existing commitment and eligible original thread state, records an account-scoped relationship event and refreshes derived search. Correspondents shows the actual open promise wording, a Recently completed ledger, and links to original promises and delivery evidence. User-set thread state remains authoritative. Saved email bodies and attachment bytes are not added by this flow.

Tests use controlled inference and synthetic Gmail with real routing, queues, SQL/RLS and encryption. They verify store mutations, question and history guards, cross-user isolation, selected-page context, unrelated versus matching attachments, cross-thread completion and replay, plus browser scroll preservation, collapsed groups, confirmations, contact filters, evidence links and mobile overflow. Live provider semantic accuracy and real Gmail behavior still require deployed verification.
